# AGENTS.md — Giftia チームの AI 利用ルール

このファイルは、Giftia チームで AI（Claude Code、Codex など）を使って開発するときのルールです。
AI はこのファイルを読んでから作業し、人間は AI に頼む前にこのファイルを確認してください。

## 1. 基本原則

- AI はコード作成・修正・調査・説明・テストなどの開発作業を**手伝う**。
- AI が作った変更は、人間が理解したうえで最終判断する。
- GitHub の重要な操作（commit・push・PR・Approve・merge）と承認は人間が行う。
- すべての変更は GitHub Flow に従って管理する。
- チームの誰もが同じルールで開発する。

> GitHub の操作と判断は人。AI はコードを書く手伝いまで。

## 2. AI の行動ルール

### Always：AI が必ず行うこと

- 作業を始める前に、目的・Issue・変更範囲を確認する。
- 作業を始める前に現在のブランチを確認する。`main` の場合は編集せず、作業ブランチへの切り替えを人間に案内する。
- 既存のコード構成と設計方針を尊重する。
- 指定されたファイルだけを変更する。
- 変更は必要最小限にする。
- 変更内容と理由を、人間が理解できるように日本語で説明する。
- 実施したテストとその結果を報告する。
- 未解決の問題や不明点を隠さずに報告する。
- [README.md](./README.md) に書かれたチームの開発ルールに従う。
- 作業が終わったら、変更したファイルの一覧と、人間に確認してほしい事項を報告する。

### Ask First：事前に人間の承認が必要なこと

- 指定されていないファイルの追加・変更・削除
- 新しいライブラリや依存関係の追加
- アプリケーションの設計変更
- データベース構造の変更
- API 仕様の変更
- 既存機能に大きな影響を与える修正
- Git の Conflict 解消案の適用
- 開発環境や設定ファイルの重要な変更
- 共有 DB への SELECT 以外の SQL（INSERT / UPDATE / DELETE を含む）の実行
- pip install の前：which python で有効な環境を確認し、人間に確かめる

### Never：AI が行ってはいけないこと

- `git commit` の実行
- `git push` の実行
- `git merge` の実行
- `main` ブランチへの直接の変更
- Pull Request の承認（Approve）・merge
- 人間の承認を経ない、GitHub Flow の重要な操作
- `.env`、API キー、パスワードなどの秘密情報の読み取りと外部への送信
- API キーやパスワードのコードへの埋め込み
- 人間の許可のない、本番環境へのデプロイや設定変更
- テストをしていないのに「成功した」と報告すること
- 指示されていないファイルの大量変更・削除
- エラーを消すためだけの対処：CORS の allow_origins=["*"]、any / @ts-ignore、例外の握りつぶし
- 親フォルダ（Step3-1_Giftia/）での npm install

## 3. GitHub Flow での役割分担

原則は **1 PR = 1 目的** です。目的が複数あるときは、ブランチと PR を分けます。

| STEP      | 作業         | 操作する人                             | 人間がやること（必須）                                                                                                                                        | AI に頼んでよいこと                                      |
| --------- | ------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 0（任意） | Issue        | 作成者                                 | GitHub で Issue を立て、番号（#1 など）を控える                                                                                                               | 「なぜ / やること / やらないこと」の下書き               |
| 1         | ブランチ     | 作成者                                 | SourceTree で最新の `main` を Pull し、`main` から作業ブランチを作る                                                                                          | なし                                                     |
| 2         | 追加・変更   | 作成者 + AI                            | やりたいことと触ってよいファイルを AI に伝える。提案を読み、分かるまで質問してから取り入れる                                                                  | 作業ブランチ上でのコードの追加・修正、エラーの意味の説明 |
| 3         | 確認         | 作成者                                 | 変更を自分で読み、差分を見る。今回のファイルだけをステージする（`.env` や関係ないファイルは入れない）。frontend と backend がこれまでどおり起動するか確かめる | 差分の説明、気になる点の洗い出し                         |
| 4         | commit・push | 作成者                                 | SourceTree で commit し、作業ブランチだけを push する                                                                                                         | コミットメッセージの案                                   |
| 5         | PR           | 作成者                                 | PR を作り、本文に「何を / なぜ / 確認手順」を自分の言葉で書く                                                                                                 | PR 本文の下書き                                          |
| 6         | レビュー     | レビュアー（作成者以外）               | Files changed で差分を見て、作業ブランチを手元で動かして確かめる                                                                                              | 気になる点の洗い出し                                     |
| 7         | Approve      | レビュアー                             | 動作を確認してから Approve する                                                                                                                               | なし                                                     |
| 8         | merge        | 人間（担当は README の班ルールに従う） | Approve が付いていることを確かめて merge する                                                                                                                 | なし                                                     |
| 9         | 全員で再現   | 全員                                   | `main` を Pull して起動を確かめ、PR に「再現 OK」とコメントする                                                                                               | なし                                                     |

- AI はコミットメッセージや PR 本文の**下書き**を作れますが、実際の GitHub 操作は人間が行います。
- PR 本文は AI の下書きをそのまま使わず、自分の言葉で書き直します（説明できないコードを入れないため）。

### PR 本文の書き方

```markdown
## 何を

（何を変えたか。1〜2 行で）

## なぜ

（どのユーザーの何が良くなるか）

## 確認手順

1.
2.

Closes #1
```

`Closes #番号` を書くと、merge したときに Issue が自動で閉じます。

## 4. コミットメッセージのルール（講師指定）

形式：

```text
種類: 何をしたか (#Issue番号)
```

| 種類       | 使うとき                |
| ---------- | ----------------------- |
| `feat`     | 新しい機能の追加        |
| `fix`      | 不具合の修正            |
| `docs`     | README などの文書の変更 |
| `refactor` | コードの整理            |
| `chore`    | 設定の変更や開発の準備  |

例：

```text
feat: 一覧画面に検索を追加 (#3)
fix: ログインエラーを修正 (#4)
docs: AI利用ルールを追加 (#1)
refactor: 検索処理を整理 (#5)
chore: 初期構成を追加 (#2)
```

AI は変更内容に合ったコミットメッセージを提案します。そのとき、次のことを守ります。

- AI 自身は commit を実行しない。
- Issue 番号がある場合は、正しい番号を使う。
- Issue 番号が分からない場合は、推測せずに人間に確認する。
- Issue がない場合の番号の扱いは、講師またはチームに確認する。

## 5. テストとレビュー

- AI が作成・変更したコードは、人間が理解してから採用する。
- 既存の frontend と backend の動作を維持する。
- 変更内容に応じたテストを行い、結果を報告する。
- テストできない場合は、その理由を書く。
- 差分に、頼んでいないファイルが含まれていないか確認する。
- `.env` や秘密情報が commit の対象に含まれていないか確認する。
- AI によるレビューは、人間によるレビューの代わりにはならない。
- AI が Conflict の解消案を出した場合も、人間が差分を確認する。

## 6. 困ったとき

| こんなとき                    | まずやること                                                                                              |
| ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| `main` に push できない       | 正常な動きです（Branch protection が `main` を守っている）。作業ブランチを作って push し、PR を出す       |
| Conflict が起きた             | 最新の `main` を作業ブランチに取り込み、`<<<<<<<` の箇所を直す。AI に頼んでもよいが、結果は自分で確かめる |
| `.env` を commit してしまった | すぐに班長と講師に連絡する。削除の commit では履歴から消えないため、接続情報を変更する                    |
| PR が大きくなりすぎた         | 目的ごとにブランチを分けて、PR を出し直す                                                                 |
| Pull したら動かない           | 依存関係をインストールし直す。それでも動かなければ PR にコメントする                                      |
